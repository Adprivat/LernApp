<objective>
Create three atomic PostgreSQL RPC functions that replace the racy client-side check-then-act pattern for challenge acceptance and tournament start.

Purpose: The root cause of BUG-01 is that `joinOpenChallenge()`, `respondToChallenge(accept)`, and `startTournament()` each perform multiple separate Supabase calls with no atomicity guarantee. Between reading `status = 'pending'` and writing `status = 'accepted'`, a concurrent caller can slip through and create a duplicate game session. Moving the entire check-claim-create flow into a single plpgsql function eliminates this race condition because PostgreSQL's `UPDATE ... WHERE status = 'pending' RETURNING *` acquires a row-level lock atomically.

Output: Three `CREATE OR REPLACE FUNCTION` blocks appended to `supabase/schema.sql`.
</objective>

**Function 1: `public.accept_open_challenge(p_challenge_id uuid, p_joiner_id uuid) RETURNS jsonb`**

Language: plpgsql, SECURITY DEFINER (matches existing `update_player_stats` convention).

Body (in order):
1. Auth guard: `IF p_joiner_id IS DISTINCT FROM auth.uid() THEN RAISE EXCEPTION 'unauthorized' USING HINT = 'unauthorized'; END IF;`
2. Atomic claim: `UPDATE public.challenges SET status = 'accepted', challenged_id = p_joiner_id WHERE id = p_challenge_id AND status = 'pending' AND is_open = true AND challenger_id != p_joiner_id AND expires_at > now() RETURNING * INTO v_challenge;`
3. Guard: `IF v_challenge.id IS NULL THEN RAISE EXCEPTION 'challenge_already_accepted' USING DETAIL = 'Diese Herausforderung wurde bereits von einem anderen Spieler angenommen.', HINT = 'already_accepted'; END IF;`
4. Create game session: `INSERT INTO public.game_sessions (mode, status, category, question_count, time_per_question, current_question_index, host_id) VALUES ('challenge', 'waiting', v_challenge.category, v_challenge.question_count, 20, 0, v_challenge.challenger_id) RETURNING id INTO v_session_id;`
5. Link session: `UPDATE public.challenges SET session_id = v_session_id WHERE id = v_challenge.id;`
6. Notify challenger: Look up joiner username from `public.profiles`, then `INSERT INTO public.notifications (user_id, type, title, message, data, is_read) VALUES (v_challenge.challenger_id, 'challenge_accepted', 'Jemand hat deine offene Herausforderung angenommen!', v_joiner_name || ' spielt gegen dich!', jsonb_build_object('session_id', v_session_id), false);`
7. Return: `RETURN jsonb_build_object('session_id', v_session_id);`

Declare variables: `v_challenge public.challenges%ROWTYPE; v_session_id uuid; v_joiner_name text;`

**Function 2: `public.accept_targeted_challenge(p_challenge_id uuid, p_acceptor_id uuid) RETURNS jsonb`**

Same pattern with these differences:
- Auth guard checks `p_acceptor_id` against `auth.uid()`
- UPDATE WHERE: `id = p_challenge_id AND status = 'pending' AND challenged_id = p_acceptor_id AND expires_at > now()` (no `is_open` check, validates `challenged_id` matches the acceptor)
- Error HINT: `'already_accepted'` (same hint so client uses same handler)
- Error DETAIL: `'Herausforderung nicht mehr verfuegbar.'`
- Notification message: `v_acceptor_name || ' hat deine Herausforderung angenommen!'`
- Notification title: `'Herausforderung angenommen!'`

Do NOT insert `game_players` rows inside either function (per research recommendation — gameStore.joinSession handles this after redirect).

Use `CREATE OR REPLACE FUNCTION` so the SQL is idempotent and safe to re-run.

**Function: `public.start_tournament(p_tournament_id uuid, p_starter_id uuid) RETURNS jsonb`**

Language: plpgsql, SECURITY DEFINER.

Body (in order):
1. Auth guard: `IF p_starter_id IS DISTINCT FROM auth.uid() THEN RAISE EXCEPTION 'unauthorized' USING HINT = 'unauthorized'; END IF;`
2. Atomic claim: `UPDATE public.tournaments SET status = 'active', started_at = now(), current_round = 1 WHERE id = p_tournament_id AND status = 'registering' RETURNING * INTO v_tournament;`
3. Guard: `IF v_tournament.id IS NULL THEN RAISE EXCEPTION 'tournament_already_started' USING DETAIL = 'Dieses Turnier wurde bereits gestartet.', HINT = 'already_started'; END IF;`
4. Create game session: `INSERT INTO public.game_sessions (mode, status, category, question_count, time_per_question, current_question_index, host_id, tournament_id) VALUES ('tournament', 'active', v_tournament.category, v_tournament.question_count, 20, 0, p_starter_id, v_tournament.id) RETURNING id INTO v_session_id;`
5. Insert game_players for all participants (tournament is different from challenges — players are pre-registered):
```sql
FOR v_participant IN
  SELECT user_id FROM public.tournament_participants
  WHERE tournament_id = p_tournament_id
LOOP
  INSERT INTO public.game_players (
    session_id, user_id, score, correct_answers,
    wrong_answers, is_ready, is_finished
  ) VALUES (
    v_session_id, v_participant.user_id, 0, 0, 0, true, false
  );
END LOOP;
```
6. Return: `RETURN jsonb_build_object('session_id', v_session_id);`

Declare variables: `v_tournament public.tournaments%ROWTYPE; v_session_id uuid; v_participant record;`

NOTE: Unlike the challenge functions, `start_tournament` DOES insert `game_players` because tournament participants are already registered and the current `startTournament()` in TournamentPage.tsx (lines 100-136) does this inline. Moving it into the RPC keeps the same behavior atomically.

Use `CREATE OR REPLACE FUNCTION` for idempotency.
